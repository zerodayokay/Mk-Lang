# jsonl (app)

**Task.** A JSON log transform, the kind of program a user writes to summarise an event log (tests/bench/README.md "Applications"). `jsonl <file> [<lines>]` reads at most `<lines>` lines of the file (all of them when absent) and writes one report to stdout. Every language does these steps, in this order, with its own standard library or, for Rust, the libraries named below:

1. **Read.** Open the file and read it through a buffered reader with a 64 KiB buffer, one line at a time. A line ends at a line feed, which is not part of it; a carriage return before the line feed is dropped by Mk's `Reader.Line`, Go's `Scanner` and the Rust program, and read as JSON white space by Zig's `std.json`. A line longer than the 64 KiB buffer is refused by Mk, Go and Zig and read by the Rust program, whose `read_line` grows its `String` (checked on 2026-11-16); the generated lines are far shorter. The program holds one line at a time: it does not read the whole file into memory.
2. **Decode.** Decode each line with the JSON library into a typed record of all ten members, by name: `id`, `status`, `bytes`, `ms` and `delta` as signed 64-bit integers, `user`, `event` and `msg` as strings with their escapes decoded, `ok` as a boolean, and `tags` as a list of strings. Each program uses its library's typed decode and no tree of its own; Mk's goes through `json.Parse`'s `Value`, because the `FromJson` that `gen json.Codec` writes takes one. A line that does not decode is an error, and the program exits 1. What decodes is each library's default (Cells, "What decodes"), and the generated input decodes in every one.
3. **Filter.** Count every line in `lines`. A record whose `ok` is false is counted in `dropped` and goes no further; the others are counted in `kept`.
4. **Aggregate.** Group the kept records by `user` in the language's standard hash map, keyed by the user name. A new group copies the name once, and takes `first`, `ms_min` and `ms_max` from its first record. Each record of the group then adds 1 to `count`, its `bytes` to `bytes`, its `delta` to `delta`, its number of tags to `tags`, the length of its decoded `msg` in UTF-8 bytes to `msg`, 1 to `buys` when its `event` is `"buy"`, and 1 to `fails` when its `status` is 400 or more; `ms_min` and `ms_max` keep the least and the greatest `ms`.
5. **Sort.** Sort the groups by `count`, greatest first, then by `bytes`, greatest first, then by `user` in byte order. No two groups share a user, so the order is total and every sort, stable or not, gives the same one.
6. **Report.** Serialise one value with the JSON library, from a typed record, as compact JSON (no white space) with the members in this order, then write a line feed:

   ```
   {"lines":L,"kept":K,"dropped":D,"groups":[{"user":"u35","count":C,"first":I,"bytes":B,"ms_min":A,"ms_max":Z,"delta":S,"tags":T,"msg":M,"buys":Y,"fails":F},...]}
   ```

   The groups come in the order of step 5. Stdout is buffered.

**Input.** `tools/bench gen` kind `jsonl`, seed 11, 400,000,000 bytes (`tools/bench/gen_app.go` `genJSONL`): one object a line, its members in one order with no white space, 2,246,091 lines at this size, 1,123,434 of them `ok`, in 4,085 groups (the Go cell's report on the whole file, read on 2026-11-15). `user` is `u0` to `u4095`, skewed toward the low ones; `event` is one of eight names; integers only; one `msg` in four carries one of eight escapes (`\"`, `\\`, `\n`, `\t`, `\/`, and the `\u` escapes of U+00E9, U+03A9 and, as a surrogate pair, U+1F600), so step 4's UTF-8 length is that of the decoded text.

**Checksum.** `"digest": true`: the SHA-256 of the whole stdout. The report's strings are the user names, ASCII letters and digits only, and its numbers are integers, so no two libraries need to write a value differently (Go's `<`, `>` and `&` escapes never arise, and no float spelling is involved). A wrong count anywhere changes the digest.

- **Rust's libraries** (`rs/Cargo.toml`, pinned by `rs/Cargo.lock`; cargo reads them from Mk-evidence's `crates/serde-1.0.229-serde_json-1.0.150`, a `cargo vendor` tree that tools/bench checks against each package's crates.io archive before every build, bench.json's `crates`): `serde 1.0.229` with its `derive` feature and `serde_json 1.0.150`. bench.json's `libs` says what each holds: serde_json's own reader and writer use unsafe Rust, its number text comes from itoa and zmij (unsafe Rust), and it scans strings with its own word-at-a-time loop (unsafe pointer arithmetic); memchr (unsafe Rust and SIMD) is linked for raw byte strings and error positions, which this row does not reach (serde_json 1.0.150 `read.rs`, read on 2026-11-16). The program's own source may use none of these. The cell is `eco (not classed)`.
- **Go's JSON.** The Go cell uses `encoding/json`'s v1 API, as real.md 5.3 names it and most Go code does. In Go 1.27.3, with its default experiments (tools/bench does not pin `GOEXPERIMENT`: its Go build takes the environment's), that API runs on `encoding/json/v2`'s engine with the v1 options: `Unmarshal` calls `jsonv2.Unmarshal(data, v, DefaultOptionsV1())` (`src/encoding/json/v2_decode.go`) and `Encoder.Encode` calls `jsonv2.MarshalEncode` under the same options (`v2_stream.go`). Go's verdicts in "What decodes" below are those of the v1 options.
- **Hash maps.** Each language's default map, with its default hash. Mk's and Zig's are fixed and resist no chosen keys; Rust's and Go's are seeded at run time (Rust's per `RandomState`, Go's per map). The user names are the file's, so a real tool fed untrusted logs would pick a keyed map (Mk `Map.NewKeyed`), as wordfreq's `mk-keyed` cell measures; this row prices each library's default.
- **Strings.** Zig's `parseFromSliceLeaky` leaves a string with no escape as a view of the line (`alloc_if_needed`, its default); Mk's `FromJson` copies every string into the line arena, and Go and Rust allocate each one: Rust's from its global allocator (the Windows process heap), freed at the end of its line, except a new group's `user`, which becomes the map's key, and Go's on its garbage-collected heap. So Mk's per-line strings, and Zig's escaped ones, come from a line arena reset per line, and Rust's and Go's from the general heap. Those are the libraries' own choices, and the row keeps them.
- **UTF-8.** Mk's `Reader.Line` and Rust's `read_line` check that each line is UTF-8; Go's `Scanner` and Zig's `takeDelimiter` do not, and leave the bytes to their JSON decoders. Also the libraries' own choices.
- **What decodes.** Each library's default, which differs on input the generator never writes (probes of 2026-11-15 and 2026-11-16 on the six cells `bench verify` built): Go accepts a missing member (read as 0), `null` for any member (read as its zero value, so `"ok":null` drops the record), a member name in another case (the v1 options match names case-insensitively, so `"BYTES"` after `"bytes"` overrides it for Go, while Mk and Rust ignore it and Zig refuses it), a byte that is not UTF-8 (read as U+FFFD) and a lone surrogate escape; Zig alone refuses an unknown member and alone accepts `5.0` for an integer; Rust alone refuses `-0` for an integer (serde_json reads it as a float); Rust and Zig refuse a duplicate member, of which Mk and Go take the last. Every library refuses trailing text, an empty line, a raw control character, an integer out of the i64 range and a string for a boolean. The generated input has none of the shapes they differ on (no `null`, only the lowercase names, `0` and never `-0`, lines of about 200 bytes), so every cell does the same work on it.
- **Who wrote the cells.** One author wrote the Mk program and all three twins. A second reader checked every cell for fairness in two rounds before the row was accepted (2026-11-16).

**Sizes.** Quick `{data} 20000` (the first 20,000 lines), publish `{data}` (the whole file). Overflow class `never`: every sum is a plain `+`, checked in mk, rust-ovf and zig-safe, wrapping in rust and go, and undefined in zig-fast (tests/bench/README.md, "Overflow"); at this size the largest, a group's `bytes`, is 1,417,353,362,070 in the same report. The size is provisional: in `verify -publish-size` runs on a shared machine (2026-11-15), the fastest cell ran under the 1 s floor on a 50,000,000-byte file and above it on this one, which is why the size was raised; the publish window confirms it with `verify -publish-size`, as every app row's. The first 20,000 lines do not depend on the size, so the quick checksum stays.
