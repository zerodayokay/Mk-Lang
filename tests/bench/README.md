# Benchmarks: the contract

Every comparison Mk publishes compares like with like. A comparison that cannot meet this contract is not published, and a baseline that cannot meet it is left out with the reason in its row's `bench.json` (`skip`). Every baseline is checked against this file before its number counts.

`go run ./tools/bench` is the only way a number gets into `RESULTS.md`.

## Tables, never mixed

| Table | Directory | Measures | Timing |
|---|---|---|---|
| `same` | `same/<row>/` | The compilers: one reference algorithm, written in every language with the same data structures, loop structure and arithmetic types | Whole programs, from outside, by hyperfine |
| `startup` | `startup/hello/` | Process start and one line of output. Reported, never subtracted from another row | Whole programs, by hyperfine |
| `codegen` | `codegen/<kernel>/` | Mk's code generator against clang 21 on the same LLVM, with no process or I/O noise | In process, by the kernel's own harness. Never feeds a cross-language ratio |
| `idiomatic` | `idiomatic/<row>/` | The standard libraries: one task, each language's std in its idiomatic form | Whole programs, by hyperfine |
| `simd` | `simd/<row>/` | Each language's SIMD layer on one vector kernel, at a fixed CPU target, at L1, L3 and DRAM sizes | Whole programs, by hyperfine; GB/s |
| `app` | `app/<row>/` | Real programs that use std: one task, each language's program, each cell labelled by its kind (`std`, `eco`, `hand`) | Whole programs, by hyperfine; peak memory read once per cell, untimed, as a fact |
| `compile` | generated by `tools/bench compile` into the work directory | The compilers' own speed on one generated program, with a Linux run of its Mk builds | Builds, timed by tools/bench's clock; a table of its own, never mixed with run time |
| `compile-real` | dogfoods of `Dogfoods/`, copied into the work directory | Mk's build speed on real programs, across mk binaries | Builds, timed by tools/bench's clock; Mk only |
| `pgo` | the rows of `same` | Mk with and without a profile of each row's own workload, labelled ("PGO table" below) | Whole programs, by hyperfine; Mk only, never mixed with another table |
| `buildtime` | the rows of `same`, `idiomatic` and `app` | How long each column takes to build the executable its run-time table times, from empty caches | Builds, timed by tools/bench's clock; no class, no bar |

The `app` table's contract is the section "Applications" below.

Extra rows live under `tests/bench-lanes/<group>/<row>/bench.json` with the same format, and `tools/bench` finds them. Their id is `<group>/<row>`.

## A row

```
same/<row>/
  README.md            the reference algorithm in prose and pseudo-code, the overflow class, the sizes
  bench.json           table, args (publish size), quick (verify size), checksums, sources, skips, notes
  mk/                  the Mk side, a package root (pkg.mk and <row>.mk)
  mkwrap/              optional: the Mk side with the wrapping operators (see Overflow)
  <row>.c  <row>.rs  <row>.zig
  testdata/<row>.go    Go sits under testdata so that ./..., go vet and internal/archtest never see it
```

Every program takes its sizes and seed from its arguments, so no optimizer can fold the work, and prints exactly one line: the checksum, a decimal integer (a counting build prints one more, below). The runner rejects a run whose checksum differs from the row's recorded one, or, before one is recorded, from the other columns'. A float row prints an integer derived from its result (for example the energy times 1e9, truncated), so the check stays exact.

A row that reads a file gives a `data` spec in `bench.json` (`kind`, `file`, `bytes`, `seed`; the kinds are in `tools/bench/gen.go`) and writes `{data}` in `args` or `quick`: before any run, `tools/bench` writes the file into `data/` from the spec (unless an up-to-date one is there) and replaces `{data}` with its absolute path. `same/jsonscan` is the example.

The header comment of every baseline file states its algorithm and everything a reader needs to judge fairness: the data structure, how it is indexed, the integer types, what is checked, and anything a language forced.

### Counting builds

A matching checksum shows that the outputs agree, not that the algorithms do: a different sort, probe sequence or loop start can print the same checksum. So a row with data-dependent control flow has operation counters:

- `bench.json` names them in `counts`, in print order, and every language has a counting build of the row.
- The counting build prints one more line after the checksum: `counts <name>=<n> ...`.
- `tools/bench verify` and `tools/bench publish` run every language's counting build at the quick size. They require the same line from all of them before the row is timed.
- `publish` excludes a language whose line differs from the line a majority of the languages print, with both lines as the reason. When no line has a majority, it excludes every cell of the row.
- `publish` records the agreed line in `results.json`.

How each language is switched, with the counters dead code in every timed build:

| Language | Counting build | The source holds |
|---|---|---|
| C | `-DBENCH_COUNT=1` | `#ifndef BENCH_COUNT` / `#define BENCH_COUNT 0`, and `if (BENCH_COUNT) { ... }` at each site |
| Rust | `--cfg bench_count` | `if cfg!(bench_count) { ... }`, the counters `static AtomicU64` (no `unsafe`) |
| Zig | a copy with the line flipped | exactly one line `const bench_count = false;` |
| Go | a copy with the line flipped | exactly one line `const benchCount = false` |
| C# | a copy with the line flipped | exactly one line `const bool BenchCount = false;` |
| Mk | a copy of the package with the line flipped | exactly one line `const BenchCount: bool = false`; counters are `var` globals of `atomic.AtomicInt` (a global `var` must be a `Share` type) |

Zig and Go take a copy instead of `-Dcount` and `-tags count`: the rows are single files built by `zig build-exe` (there is no `build.zig` to carry a `-D` option) and `go build <file>.go` (a build tag selects files, not a constant inside the one file). `tools/bench` writes the copies under `<work>/count-src/` and refuses a source whose switch line is missing or appears twice. Zig counts in ReleaseSafe, Rust in the `rust` column's flags; the `rust-ovf` and `zig-fast` columns compile the same file as their language's counted column. `mk-wrap` is not counted: it is a separate source (`mkwrap/`) with no switch, which differs from `mk/` only in the wrapping operators (checked by reading the diff).

A row whose operation count is fixed by its arguments, or is already its checksum, says so in `no_counts` instead (for example `mandelbrot`, whose checksum is the total number of escape-loop iterations); `TestTreeRowsMeetTheContract` requires one or the other on every same-algorithm row. Counted: `sieve` (`marks`, the stores of the inner loop, which catch a loop started at `2i` instead of `i*i`) and `sortints` (`pdq` loop iterations, `ins` insertion sorts and their `shift` moves, `heap` heapsorts, `rev` reversed ranges, `part` and `parteq` partitions, `pis` partial insertion sorts, `brk` pattern breaks: the whole recursion shape of the pdqsort).

## Same algorithm

- One algorithm, written once in the row's README, then in Mk, C, Rust, Zig and Go with the same data structures, the same loop structure and the same arithmetic types.
- No intrinsics, no hand vectorisation, no `-ffast-math`, no per-language tuning. The Benchmarks Game's tuned programs are not the model.
- No hints: `TestTreeRowsMeetTheContract` refuses, outside comments, `restrict`, `#pragma`, `__builtin_*`, attributes and `inline` in C; `unsafe`, `std::hint`, `target_feature` and `#[inline]` in Rust; `@setFloatMode`, `@branchHint`, `@prefetch` and forced `inline` in Zig; `import "unsafe"` and `//go:` directives in Go; `unsafe`, `stackalloc` (in the `same` table), `[MethodImpl(AggressiveInlining|AggressiveOptimization)]`, `System.Runtime.Intrinsics` (outside `simd`), `Unsafe.*`, `MemoryMarshal.Get*Reference` and `System.Numerics.Vector<T>` (outside `simd`) in C#; `std.simd` and unsafe modules in Mk.
- No unchecked indexing anywhere: no `get_unchecked` or unchecked slicing in Rust, no `@setRuntimeSafety(false)` in Zig. C and Zig ReleaseFast are the unchecked ceiling and are labelled so. The optimizer may remove a bounds check it can prove, in every checked column alike.
- Inputs come from splitmix64 (below) with a stated seed, or from a file `tools/bench gen` writes from the row's `data` spec. Byte-identical across languages.
- Single-threaded. `tools/bench publish` pins itself to one logical CPU (affinity mask `0x4`, whose SMT sibling stays idle) and every program inherits the mask. Every program `tools/bench` runs (verify, the counting builds, hyperfine, compare) gets `GOGC=100` and `GOMAXPROCS=1` set and `GODEBUG`, `GOMEMLIMIT`, `GOTRACEBACK`, the Mk runtime's `MK_CARRIERS`, `MK_IO`, `MK_PROFILE_DIR`, `MK_INHERIT` and every `MK_TEST_*` cleared, whatever the caller's shell holds; the facts print the values read back from that environment (`tools/bench/env.go`).
- Allocation is outside what a row measures unless the row is about allocation. `binary-trees` states its allocator in the pseudo-code: one preallocated buffer and a bump index, the same in every language.

### Overflow

Each row states its overflow class in `bench.json`:
- `never`: no input of the stated sizes overflows. C uses signed types (overflow is UB, the licence for `nsw`), Zig plain `+` (UB in ReleaseFast, a panic in ReleaseSafe), Rust plain `+` (wraps at `opt-level=3`, panics in the `rust-ovf` column), Go wraps, and Mk's `+` panics.
- `wraps`: the algorithm wraps by design (hashes, LCGs). C uses `uint64_t`, Zig `+%`, Rust `wrapping_*`, Go plain operators, Mk `+%`.

Where Mk checks and others do not, a second Mk column, `mk-wrap`, writes the same algorithm with the wrapping operators. It still emits no `nsw`, so it is not C's semantics either; it prices Mk's overflow check in the row's own arithmetic. Bounds checks stay on in both Mk columns. The language has no switch to remove a check; the prices of Mk's two check budgets come from the check-budget table below, built with `mk build`'s hidden benchmark-only flags.

Every Mk build gets `MK_STD` set in its environment: empty (the std embedded in the mk measured) unless `tools/bench -mk-std <dir>` names a std tree, and the value is recorded with the command and in the run's facts, so an `MK_STD` inherited from the caller cannot change a build unseen.

Safety classes: `checked` (bounds and overflow), `bounds` (bounds only), `unchecked`. `RESULTS.md` gives each cell's ratio to the fastest cell of its row and to the fastest cell of its class. Each column's toolchain version, LLVM version, LTO mode, linker, CRT linkage and whether its precompiled std is built for x86-64-v2 are printed in the table header. Only Mk and C share an LLVM: Mk against C is the codegen metric (the gate's median ratio to C uses that pair only), and Rust, Zig and Go are toolchain comparisons.

Against Rust and Zig, on the `same` table, mk is held within 1.00, by the bootstrap interval, of the faster of `rust-ovf` and `zig-safe`, because Mk keeps its checks. That peer is chosen by the column's build facts, as the std bars choose theirs, so a `wraps` row such as `jsonscan`, where the overflow class makes every column `bounds`, still has one. RESULTS.md has no column for this bar: it is read from the row's `rust-ovf` and `zig-safe` cells (each one's median and ratio to the row's best, with its interval, in the row's table), not from the "Ratio to best of its class" column, which follows the overflow class. The row's best cell over every column (C, `zig-fast`, `rust`, `go`) is reported beside it. The idiomatic table's bar is the std bars' 1.25, below. Go is not in the checked class: it checks bounds but wraps on overflow, so its cells are reported, never the target.

PGO is off in every column, outside the labelled PGO table below. Mk would read a `default.mkprof` in the package root and Go a `default.pgo` beside its main package, so `tools/bench` refuses to run while either exists anywhere under `tests/bench` or `tests/bench-lanes`.

## Timing

- `tools/bench publish [rows]` holds the machine lock of `tools/machinelock` (shared with `tools/gate`; where it and the work directory live: [Work directories](../../CONTRIBUTING.md#work-directories)) for the whole run, builds every column, checks every checksum at the publish size, pins its affinity, and then times each cell with `hyperfine -N --warmup 3 --runs 10 --export-json`, in three sweeps with the columns in rotated order, pooling at least 30 runs per cell. A cell whose relative standard deviation is above 3 percent is rerun once and then marked noisy.
- Publish sizes are chosen so the fastest cell of the row runs at least 1 s; a row below that floor says so in `RESULTS.md`.
- Ratios carry a 95 percent bootstrap interval of the ratio of medians (10,000 resamples, fixed seed). A cell is "over" a threshold when the whole interval is above it, "within" when it is below, otherwise "inconclusive". Bars and gates cite the class, not the point ratio.
- `tools/bench compare --base <old mk> --head <new mk> <rows>` builds the Mk columns with both compilers, checks their checksums, runs A and B alternately (ABBA) in one invocation and prints the paired ratio with its interval. It holds no lock, and its output says PROVISIONAL: it is for development, never a published number.
- A column is rebuilt only when its stamp changes: the command, its environment, the toolchain's version text (`clang --version`, `rustc -vV`, `zig version`, `go version`, `mk version`, the same strings the facts print), the row's sources, the mk executable and, for an Mk build with `-mk-std`, every file of that std tree.
- `publish` merges into an existing `results/<date>/` only when the kept rows were measured with the same mk binary, std and toolchain versions; otherwise it refuses, so one table states one toolchain and one mk / c median. The mk of the facts is named by the commit embedded in the binary (`vcs.revision`), not the working tree's HEAD.
- `publish -resume` (for a run that died, the same rows and date again) reuses each raw export the dead run left in `results/<date>/raw/` instead of timing that sweep or rerun again, but only when the export names the same program and arguments, holds the run count, and was written after the program was built (`resumeRaw`); each reused file is listed in the cell's `resumed` field of `results.json`. A publish otherwise writes `results.json` only at its end.
- `tools/bench verify [rows]` builds and runs every column at the quick size (`-publish-size` for the publish size) and checks the checksums. A row is timed only after it verifies.
- `tools/bench render [-date D]` rewrites `RESULTS.md` from `results/<D>/results.json` with no build and no timing (after a change to the renderer).
- **What may run on a busy machine.** `tools/bench verify` at the quick size and `go test ./tools/bench` time nothing. Every timed run (`publish`, `compare`, `codegen`, `compile` and `compile -real`, `compile-linux`, `buildtime`, `http`, anything under `MK_TIMING`) and every Linux run waits for a quiet machine. A development decision rests on instruction and cycle counts (`perf stat -e cycles,instructions` in WSL) and on provisional `compare` pairs; a published before and after is one final `publish` per table, in one quiet window.

Each results directory `results/<date>/` holds `results.json` (the facts, every build command, every cell's raw times and summary) and `raw/<row>/<column>.<sweep>.json` (hyperfine's own export). Every table records the commit, the mk binary's SHA-256, the CPU, the OS, the power scheme, Defender's real-time state, the affinity, the toolchain versions, and the compilers and test binaries already running when it started. `RESULTS.md` is rendered from one date's `results.json`; a section that date did not measure (codegen, Linux, compile speed and its Linux run, the real-program compile table, the build-time table, http) is carried from the newest earlier date that has it, under that date's name and with a line saying it was carried, never merged into the date's rows.

## Check budgets

Mk sets two run-time budgets on the same-algorithm table: bounds checks at most 3 percent median, overflow checks at most 5 percent median. Their prices come from Mk against itself, never from another language:

```
tools/bench publish -budgets -mk <mk.exe> [-mk-std <std dir>] [-date D] [rows]
```

- For every same-algorithm row with an `mk` source, one mk executable builds the `mk` program three ways: as published (`mk`), with `--no-bounds-checks` (`mk-nobounds`) and with `--no-overflow-checks` (`mk-noovf`); plus `mk-wrap` where the row has one. The flags are hidden, benchmark-only flags of `mk build` (they set `driver.Config.TestHooks.NoBoundsChecks` and `NoOverflowChecks`). The mk measured must have them; older mk binaries do not.
- The price of a check is the ratio of medians, checked over unchecked (`mk / mk-nobounds`, `mk / mk-noovf`), with the 95 percent bootstrap interval; the section gives each row's price and the median over the rows against the budget. `mk / mk-wrap` is printed beside the overflow price: both flags remove a check from the whole program, std included, while `mk-wrap` changes only the row's own operators, so the two overflow numbers are different measurements. In a `wraps` row the row's arithmetic already wraps and `mk-noovf` changes only std.
- The verdict against each budget cites the 95 percent bootstrap interval of the median price (rows fixed, every row's times resampled): within when the whole interval is below the budget, over when it is above, otherwise inconclusive.
- Each unchecked program must print the row's checksum, which is checked before it is timed. Timing, the lock, the affinity and the sweeps are those of `publish`; the counting builds are not repeated (they are a property of the sources, checked by the same table's publish).
- Results go to `results/<date>/budgets/results.json` and its `raw/`, and `RESULTS.md` gets a "Check budgets" section after the other tables. The section's `mk` may differ from the same-algorithm table's (its facts say which binary and which std), so its cells are compared only with each other, and nothing in it feeds a cross-language ratio.
- `tools/bench verify -budgets [rows]` builds and checks these columns too, and `tools/bench compare -cols mk-nobounds ...` compares two mk executables on one of them.

## PGO table

PGO is off in every column of every other table. The one place it is on is a labelled table of its own, Mk against itself:

```
tools/bench publish -pgo -mk <mk.exe> [-mk-std <std dir>] [-date D] [rows]
```

- For every same-algorithm row with an `mk` source, one mk executable builds the row's `mk` program twice: as in every other table (`mk`, `--pgo=off`), and with the row's own profile (`mk-pgo`, `--pgo=<profile>`).
- **Training.** The profile comes from one training run per row: the program built with `--pgo-gen`, run once at the row's quick arguments (`bench.json` `quick`) in the row's environment with `MK_PROFILE_DIR` set to a fresh directory under the work directory (every other run has it cleared), its output checked against the row's quick checksum, and what it wrote merged by `mk profile merge` into `<work>/pgo/<row>/<row>.mkprof`. The profile stays in the work directory, never in the tree, so the refusal of a `default.mkprof` under the benchmark trees is unchanged. A row is trained again only when its instrumented program or its quick arguments change; the profile's bytes are in `mk-pgo`'s build stamp.
- **What it measures.** The profile is trained on the row's own input at a smaller size, the favourable case for PGO: a profile from another workload may give less. The section prints each row's `mk` and `mk-pgo` cells and the ratio of medians `mk-pgo / mk` with its 95 percent bootstrap interval (under 1 is faster with the profile), and the median over the rows with its bootstrap interval. It has no bar and gates nothing.
- **Never mixed.** `mk-pgo` is in no other table: it is not a column of `list`, `verify`, `compare` or `publish` without `-pgo`, and nothing in the section feeds a cross-language ratio, the median mk / c, a budget or a std bar. The section's `mk` may differ from the same-algorithm table's (its facts say which), so its cells are compared only with each other.
- Each program must print the row's checksum, which is checked before it is timed; a row whose training or `mk-pgo` build fails has that cell excluded with the reason. Timing, the lock, the affinity and the sweeps are those of `publish`; the counting builds are not repeated.
- Results go to `results/<date>/pgo/results.json` and its `raw/`, and `RESULTS.md` gets a "PGO" section after the check budgets. `tools/bench verify -pgo [rows]` trains, builds and checks both columns without timing anything.

## Inputs: splitmix64

```
state x = seed
next():  x = x + 0x9e3779b97f4a7c15            (mod 2^64)
         z = x
         z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9 (mod 2^64)
         z = (z ^ (z >> 27)) * 0x94d049bb133111eb (mod 2^64)
         return z ^ (z >> 31)
```

Steele, Lea and Flood, "Fast splittable pseudorandom number generators" (OOPSLA 2014), as in Vigna's `splitmix64.c`. For seed 0 the first outputs are `0xe220a8397b1dcdaf`, `0x6e789e6aa1b965f4` (`TestSplitmixReference`). Data files are written by `go run ./tools/bench gen` into `data/`, which is git-ignored and regenerated on demand; a `<file>.spec` stamp beside each file names the spec it came from.

## The codegen table

The in-process Mk-against-C harness is a table of its own. It measures Mk's code generator against clang 21 on the same LLVM, with no process start or I/O in the number, and it never feeds a cross-language ratio. Kernels: `intsum`, `sieve`, `matmul`, `nbody`, `fmtints` (the same algorithms as the `same` rows of those names; binary trees is `same/binarytrees`).

```
go run ./tools/bench codegen -mk <mk.exe> [-quick] [kernels]      build, check, provisional times (no lock)
go run ./tools/bench codegen -mk <mk.exe> -publish [-procs 3] [-date D] [kernels]
```

**A kernel** is `codegen/<kernel>/`:
- `<kernel>.c`, the C side: one freestanding C file (`stdint.h` only, no C library), opening with a header that states the algorithm and what a reader needs to judge fairness. It exports `bench_c_<kernel>_fill` and `bench_c_<kernel>_run` over 64-byte-aligned static buffers of fixed capacity; the loop bound comes in at run time.
- `<kernel>.mk`, `pkg.mk` and `ref/ref.mk`: the Mk side and the harness. `ref` is the package's one unsafe module, holding the `extern` declarations of the C functions. Mk's `Fill` and `Run` are the C side's algorithm, line for line, on arena slices aligned to 64 bytes (the slice's address comes from a C helper that reads the slice header, because a package outside std cannot import `std.raw` at the mk measured; `Main` refuses to run on a misaligned buffer).
- `codegen.json`: `name`, `algorithm`, `measures` (what the ratio prices, such as "Mk's checked + and bounds checks against C's `add nsw`"), `c`, `args` and `quick` (the program's arguments before the round count), `checksum` and `quick_checksum`, and `rounds` (at least 21). It is not a `bench.json`, so the hyperfine tables never see a kernel.

**The harness.** `Main` reads its sizes and seed from argv, so neither optimizer can fold the inputs. Each round runs both sides, Mk first on even rounds and C first on odd ones; each side fills its own buffers untimed, then times only its `Run` with `time.Now` and prints `round <r> mk <ns> <checksum> c <ns> <checksum>`. `tools/bench` rejects a run where any round's checksum, on either side, differs from `codegen.json`'s. The checksums were cross-checked against the `same` rows, whose five-language agreement is in their `bench.json`: `sieve` 664579 (the primes up to 10^7), `fmtints` 499688088 (a hundredth of `same/fmtints`' 49968808800), `matmul` 2179172659708 (a 76th of `same/matmul`'s), `nbody` quick -112142077 (`same/nbody`'s quick checksum).

**Linking the C side.** `mk build` has no flag for an extra object at the mk measured, and the kernels leave `pkg.mk`'s `c_sources` empty. So `tools/bench` builds with `mk build --llvm <work>/codegen/<kernel>/llvm`, a directory holding copies of `tools/bench`'s own executable named `clang`, `lld-link`, `ld.lld` and `llvm-lib` plus a `bench-shim.json` (`shim.go`). Started under those names, the executable runs the real tool of that name from `C:\Program Files\LLVM\bin` with the same arguments and exit status, and appends the kernel's C object to the linker's command line only. Every forwarded command is logged, and `tools/bench` refuses a build whose link line does not name the object. The tools are the same binaries every other build uses, so the code mk emits does not change.

**Builds.**
- C: `clang --target=x86_64-pc-windows-msvc19.33.0 -std=c17 -O3 -march=x86-64-v2 -ffp-contract=off -fno-math-errno -ffreestanding -c`, the same triple mk passes clang. A native object, no LTO, so the C code is optimised once, by clang, exactly as written. `-fno-math-errno` makes `__builtin_sqrt` one `sqrtsd`, as Mk's `math.Sqrt` is. `tools/bench` runs `llvm-nm --undefined-only` on the object and refuses any undefined symbol except those the Mk runtime defines (`memcpy`, `memmove`, `memset`, `memcmp`, `bcmp`, `__chkstk`, `_fltused`), because the link is `/nodefaultlib`.
- Mk: `mk build --release --pgo=off --cpu x86-64-v2 --no-cache --llvm <shim>`, as in the `same` table: ThinLTO for the Mk code, the C object linked beside it.

**Timing (publish).** The machine lock for the whole run, affinity `0x4` inherited by the kernel programs, `-procs` processes per kernel (default 3) of `rounds` rounds each, pooled. Per side the median, minimum and MAD of the `Run` times; the ratio is median(mk) / median(c) with its bootstrap interval, classed against 1.10. The results go to `results/<date>/codegen/results.json` (with every build command), and `RESULTS.md` gets a "codegen" section after the Windows tables. Without `-publish` the numbers are printed as PROVISIONAL and written nowhere.

**Any package.** `go run ./tools/bench link [-mk <mk.exe>] [-o <out.exe>] <package dir> <file.c>` builds one Mk package with one freestanding C file linked in the same way (same flags, same symbol check, same link-line check), for `ccall` and for anyone who needs such a program.

**Windows only.** The Linux table is the same-algorithm set; the kernels' address helper relies on the Windows x64 rule that a 16-byte struct is passed by reference.

Binary trees and `sortints` are `same` rows only, and `hashmap`, `wordfreq` (which includes word counting), `sort`, `sortstable` and `sortstr` are idiomatic rows. `ccall` is a budget test of C calls from tasks and of the system-stack switch, not a comparison.

## Idiomatic standard library

`idiomatic/<row>/`: each row states a task in its README ("count the word frequencies of a 50 MB text with the standard hash map"), and each language does it with its own standard library in its idiomatic form. A row compares libraries and their algorithms, not code generators, so the counting builds do not apply (`no_counts` says so) and the checksum is taken over results every library must agree on.

- **No stand-ins.** A language whose standard library has no facility for the task has no source, and its `skip` reason is the cell ("no std JSON in Rust (serde_json is a crate)"); no third-party library or hand-written replacement stands in. A Mk side whose module does not exist yet is skipped with a reason that starts `pending:`, so a search finds them (`grep -l '"pending:' tests/bench/*/*/bench.json`).
- **Checksums over values.** Formatting and serialising rows check the parsed-back values, never the output bytes: `fmt` sums every parsed integer and the integer part of every parsed float and counts the floats that came back bit-exact; `json` walks the reparsed tree with an order-independent sum. C's `printf` has no shortest float format, so its `fmt` cell prints `%.17g` and is labelled not shortest.
- **Hashes and sorts named.** The map rows grow every map from empty and name each cell's hash and DoS posture in the row README; Mk's keyed map is its own column, `mk-keyed` (`Map.NewKeyed` with `HashKey.New`, SipHash-1-3 under a random per-process key), Rust's peer, beside `mk` (the fast fixed hash). Sorting is three rows: unstable `u64` (`sort`), stable `u64` (`sortstable`, C: no std stable sort) and strings as views into one buffer compared bytewise (`sortstr`), the `u64` rows on `same/sortints`' four patterns; C's `qsort` is labelled as an indirect comparator. A row about allocation names each cell's allocator in its README and notes the same way.
- **The std bars.** After each idiomatic table, `RESULTS.md` judges every Mk cell (`mk`, `mk-keyed`, `mk-ctx`, `mk-wrap`) of every idiomatic row, under `tests/bench` and `tests/bench-lanes`, in a section of its own, "The std bars":
  - **The 1.25 bar.** The ratio of medians to the best checked peer: the fastest cell among C, Rust, Zig and Go whose own build checks bounds and traps overflow, which means `rust-ovf` and `zig-safe`. Over 1.25 needs a written reason and a plan.
  - **The 2x rule.** The ratio to the fastest C, Rust, Zig or Go cell of any class (C and `zig-fast` are unchecked). Over 2.0 is a std defect, unless it is a stated exception: `crypto.Random` (`crypto-random`), `SortStable` (`sort-stable`). A row that is one says so in bench.json's `exception` (`"sort-stable"`), and its over verdict reads "over (sort-stable, a stated exception)" and is counted apart. The exceptions are a closed table in tools/bench (`stdExceptions`): `exception` must be crypto-random on a row whose `std` is exactly `["std.crypto.Random"]`, or sort-stable on one whose `std` is exactly `["std.core.Slice.SortStable"]`, and anything else is refused.
  - **Reported, no bar.** Each ratio classified against the other threshold: the checked peer against 2.0, the best of any class against 1.25.
  - **Verdicts** cite the 95 percent interval, as `same`'s 1.10 does: within, over or inconclusive.
  - **The peer comes from the column's facts, not from the cell's class.** In a `wraps` row the overflow class makes every column `bounds`, yet `rust-ovf` and `zig-safe` still build the row's program with overflow traps (Zig compiles its std with it; Rust's std is prebuilt), and Mk builds with every check on. Mk's own columns and the check-budget columns (`mk-nobounds`, `mk-noovf`) are never a reference, and a budget column is not judged.
  - **A row with no checked peer** (Mk and Go only, as in `spawn`) says "no checked cell" and has no 1.25 verdict.
  - **No kernel time.** A cell with its fill subtracted and any kernel time at or below 0 once its baseline is subtracted has no time to divide by, so no interval reaches 0 or infinity. An Mk cell with none is not judged and is counted under "No kernel time". A reference is still the fastest eligible cell when it has none: it is named "`<column>`: no kernel time", its ratio gives no verdict, and the line counts it under "Peer with no kernel time" or "Best with no kernel time", so a slower cell never stands in for it. The checked peer and the best of any class are judged apart, so one can give a verdict while the other has no time. Each line's Mk cells timed are its 1.25 verdicts plus "No checked peer" plus "Peer with no kernel time".
  - **Not judged:** the http row, which has its own section and measures req/s.
  - **The summary.** bench.json's optional `std` is the list of std functions the row prices, each as `std.<module>`, any lower-case names, then the exported names (`["std.core.Slice.SortStable"]`; `fmt` prices three, `["std.core.Print", "std.core.str.ParseInt", "std.core.str.ParseFloat"]`). Every tree row names its list, and `TestStdNamesInStd` checks that each name's module is under `std/` and declares its last name. One line per list, shared by the rows with the same list, and one per bench.json directory (`tests/bench/idiomatic`, `tests/bench-lanes/<lane>`) for the rows that name none, counts the verdicts. A line that counts cells of runs with different mk binaries, std or toolchains says so.
- **New std rows** go under `idiomatic/<row>/`.
- **Concurrency rows.** `spawn`, `chan` and `http` are about concurrency, so they are not pinned to one CPU: `bench.json` `concurrency` gives the affinity mask every program of the row inherits (`tools/bench` sets its own affinity to it for that row's cells), the thread count (`GOMAXPROCS` and `MK_CARRIERS`, set in the program's environment) and each language's model, which `RESULTS.md` prints beside each cell ("tasks", "goroutines", "OS threads"). Only languages whose std has the facility have a cell: `spawn` has Mk tasks and goroutines (C, Rust and Zig have OS threads only, and 1 M of them cannot be created on Windows); `chan` has Mk, Go and Rust's `mpsc` over two OS threads, labelled threads.
- **Inputs.** Text, logs, JSON and gzip files come from `tools/bench gen` kinds `words`, `log`, `json` and `gzip` (`tools/bench/gen.go`), the rest from splitmix64 inside the programs. The `app` table's kinds (`tree`, `jsonl`, `mixed`, `zlib`) are in "Applications".

- **The http row** is a server, so it has its own spec (`idiomatic/http/http.json`) and measurement, `tools/bench http [-full] [-publish]`: Mk `std.http.Serve` (tasks, `MK_CARRIERS=8`), Go `net/http` and Zig `std.http.Server` under tools/bench's load generator, 1,000 keep-alive connections, 5 s warm-up and 30 s measured, the server on CPUs 0 to 7 and the generator on 8 to 15, req/s, p50 and p99, every response checked; C and Rust "no std HTTP" (its README). Results go to `results/<date>/http/` and their own section of RESULTS.md.

Rows: `wordfreq`, `hashmap`, `sort`, `sortstable`, `sortstr`, `closuresort`, `fmt`, `json`, `regex`, `gzip`, `spawn`, `chan`, and `http`; and the std rows `search`, `listpush`, `mapiter`, `strops-find`, `strops-split`, `strops-replace` (its Mk cell on `str.Replace`), `bufwrite`, `alloc-small`, `arena-reset`, `casemap`, `mutex`, `timers` and `json-small`. The idiomatic rows under `tests/bench-lanes/` (hashes, maps and collections) use the same table name and are read the same way.

## SIMD

`simd/<row>/`: one vector kernel per row, written with each language's SIMD layer: C `<immintrin.h>`, Rust `std::arch` (portable `std::simd` is nightly-only), Zig `@Vector`, Go scalar or its assembly-backed std (labelled so), C# `System.Numerics.Vector<T>`, Mk `std.simd`'s `Vec` and `Mask` at the variant's fixed width. The same-algorithm bans on intrinsics do not apply here, and nothing else is lifted: unchecked indexing, fast-math and per-language tuning are banned in every table (`otherTableViolations` in `tools/bench/findings_simd_test.go`, run by `TestTreeRowsMeetTheContract` over every idiomatic and SIMD source: the same-algorithm list, with only the vector layer allowed here: `<immintrin.h>`, `std::arch` and the `unsafe` blocks it needs, `cfg(target_feature)`, `@Vector` and `inline for` over a row's fixed vectors, `__builtin_ctz`, `System.Numerics.Vector<T>` / `System.Runtime.Intrinsics` without `unsafe`, `std.simd`).

- **Checked loads in the checked columns.** A column's class comes from its build flags, so its source must not undo them: Rust's `std::arch` loads take a raw pointer, and each takes it from a checked slice (`&s[i..i + 128]`, then constant sub-slices) or after an `assert!` of its bound in the same function, so `rust` and `rust-ovf` are bounds-checked like `zig-safe`'s `s[i..][0..W].*` and Mk's `std.simd` loads. Pointer arithmetic (`.add`, `.offset`) with no such assert fails the contract test.
- **Aligned buffers.** Every program allocates its buffers on a 64-byte boundary itself, and refuses to run (exit 3) if one is not, so no cell measures its allocator's alignment. C and Go over-allocate by 64 bytes and take the offset to the boundary; Go reads the address through `reflect`, since `import "unsafe"` is banned. Rust takes `align_offset(64)` into an over-allocated `Vec`, and Zig calls `alignedAlloc(.., .@"64", n)`. C's `malloc` gave 48 mod 64 for 16 KiB on this machine, Rust's `Vec` 16. Mk code cannot read an address without `std.raw`, which every table bans. These cells allocate with `Arena.Slice`, which promises only the element type's alignment. So an Mk vector cell over arena buffers is the labelled exception. Its source says so. Its row's notes state the offset that a probe with `std.raw` outside the tree measured: 0 mod 64, since std's heap arenas start a slice of 4 KiB or more on a cache line. They also state what it costs: nothing, since none of the 32-byte loads cross a cache line at v3, and none of the 16-byte loads at v2. `TestArenaOffsetsAsLabelled` checks both, the offset by running a probe at every variant's size. The rows with such a cell are `indexbyte`, `dot` and `validutf8` (their width-fixed Mk cells `mkfix` and `mkfixv2`; the `str.From` cell of `validutf8-l1v2` runs `std.simd.ValidUtf8`'s vector loads over the same arena slice), and the `tests/bench-lanes` rows `lang-sys/countbyte`, `std-rewrite/d358` and `std-ws/ws-mask`. `TestReadmeNamesTheExceptions` fails when a loaded row with such a cell is not named here.
- **Fill subtracted.** Each program builds its input inside the timed run (one fill pass and, at 1 GiB, the first-touch page faults), which is scalar code each compiler vectorises differently. Each variant's `baseline` is its arguments with 0 repetitions; `publish` times it in every sweep right after each cell, and RESULTS.md reports the kernel: each run's time minus the cell's baseline median, with the ratios, intervals and GB/s from that. A row published before baselines existed (2026-11-07) says its numbers include the fill.

- **Fixed targets, no dispatch.** A row's `variants` expand it into one row per CPU target and size, `<row>-<size><target>` (`indexbyte-l1v2`, ..., `indexbyte-dramv3`). A variant's `cpu` (`x86-64-v2` or `x86-64-v3`) reaches every column's flags: C `-march`, Rust `-C target-cpu`, Zig `-mcpu` (`x86_64_v3`), Go `GOAMD64`, Mk `--cpu`. Each program picks its vector width at compile time from that target (C `__AVX2__`, Rust `cfg(target_feature = "avx2")`, Zig `std.simd.suggestVectorLength`). Nothing chooses at run time, except Go's `bytes.IndexByte` and Mk's `str.From` in `validutf8-l1v2`, each labelled. On Mk's side, `std.simd`'s byte and float routines (`IndexByte`, `IndexAny`, `Count`, `Equal`, `Compare`, `Dot`, `Sum`, `ValidUtf8`, `Dispatch`) test `Cpu()` and run a `cpu "avx2"` or `cpu "avx512bw"` body. An Mk cell of a fixed row may not call them (`mkDispatch` in `rowViolations`, `TestNoRunTimeChoiceInFixedRows`). It writes its loop with `Vec[T, L]` instead, `L` fixed per package as `mandelvec`'s `mk` and `mkv2` do, since Mk has no compile-time CPU fact. So the Mk cells of `indexbyte`, `dot` and `validutf8`'s vector variants are their width-fixed packages (`mkfix` at v3, `mkfixv2` at v2, `dot`'s one `mkfix` at both). They do not call std's dispatching routines, which run a 64-lane AVX-512 form beside 32-byte AVX2 cells. For the same reason, `lane-review.json` holds `std-simd/indexany`, `equal`, `count`, `compare` and `sum`. A cell may still reach a run-time choice through a std routine it calls. `validutf8-l1v2`'s `str.From` is std's validator as it ships, whose `std.core` `ValidUtf8` hands 256 bytes or more to `std.simd.ValidUtf8`. Such a cell is labelled by its variant's `dispatching` field (language to how), which `expand` prints in the variant's notes. `TestNoRunTimeChoiceInFixedRows` builds every Mk cell of a fixed-target row with the row's mk line. It fails on one whose executable holds a `cpuid`, unless its variant labels it (for a `tests/bench-lanes` row, its entry in `lane-review.json`). That `cpuid` is Cpu()'s detection, std's one source of it; inline assembly could also emit one, and would read the CPU's features just the same. One `tests/bench-lanes` row keeps a dispatching Mk cell, labelled: `std-rewrite/d358`, an internal comparison of std's routines as they ship against std.core's scalar ones, with no C, Rust or Zig column. The other exception is the run-time dispatch row `simd/indexdispatch`, kept outside the tree. Every column of it runs at `x86-64-v2` and picks its form at run time: Mk's `cpu` clause inside `std.simd.IndexByte`, C's `__attribute__((target(...)))` after cpuid, Rust's `#[target_feature]` after `is_x86_feature_detected!`, Go's runtime, Zig "no std dispatch". Its `bench.json` `dispatch` field labels each column's dispatch and lifts exactly those two bans for that row (`rowViolations`, `TestDispatchRow`).
- **Sizes.** Bandwidth rows run at an L1 size (16 KiB, repeated), an L3 size (32 MiB; the CPU has 96 MB of L3) and a DRAM size (1 GiB), and report GB/s from the row's `bytes` (bytes a run reads) over the median kernel time. Compute rows (`mandelvec`) report time.
- **Same bits.** The dot product states its 16 partial sums and their pairwise reduction (those of `std.simd`'s `Dot`), and no column fuses a product into a sum, so every column prints the same bits; `mandelvec`'s counts equal `same/mandelbrot`'s.

- **A variant may leave a cell out.** A variant's `skip` (language to reason) takes that language's cell out of that variant only; `validutf8` measures std's validators (Mk's `str.From`, Go's `utf8.Valid`) in `validutf8-l1v2` alone, because as scalar validators elsewhere they would run 10 to 30 times the fastest cell (its README).

Rows: `indexbyte`, `dot`, `mandelvec`, `validutf8`.

## Applications

`app/<row>/`: each row is a real program that uses its language's standard library, the kind of program a user writes. The `same` table measures compilers and the `idiomatic` table one std facility at a time; this table measures whole programs, std, runtime and compiler together.

```
app/<row>/
  README.md            the task: command line, input, every step of the work, output, and each cell's kind
  bench.json           table "app", kinds, libs, hand, env, package or sources.mk, crates, digest, output, checksums
  mk/                  a new Mk program (or "package" names a dogfood instead)
  <row>.c  <row>.zig  testdata/<row>.go
  <row>.rs, or rs/     a crate: Cargo.toml, Cargo.lock and src/main.rs
```

- **The task is the contract.** The row's README states the command line, the input files (from `tools/bench gen`, byte-identical for every language), every step of the work and the output. Same work is judged by identical input and the checksum, never by matching code shape. The counting builds do not apply, and an app row has no `counts`.
- **Every cell has a kind**, from `kinds` in bench.json, printed beside the cell:
  - `std`: the language's standard library only. Mk's cell is always `std`, so its package, and each variant's, has no `c_sources`, `c_imports`, `asm_sources` or `links`, and no `deps`: a dependency's own `c_sources`, unsafe modules and vector code apply to it and link into the program (doc/reference.md), out of reach of the checks below. A Rust crate whose `Cargo.lock` holds any package but itself is not `std`, and neither is a C cell given a `vendor` library: tools/bench refuses either labelled `std`.
  - `eco`: named libraries pinned to an exact version, listed in `libs`, each with its name, its version, the language it is written in, and what is inside it that the program's own source may not use (unsafe code, SIMD, C, assembly), or `none`. For example Rust `flate2 1.1.1` (Rust; inside: `miniz_oxide`, pure Rust), C `zlib 1.3.1`.
  - `hand`: the program writes a facility itself, and `hand` says what and its line count ("a CSV splitter, 40 lines").
  - A structure that the row's README makes part of the task, which every cell must therefore build, is not a facility and is counted as `hand` in no cell: `app/orderbook`'s slot pool with generations and its bitset of live arrival numbers.
  - There are no tool columns such as `rg` or GNU grep. C may walk a directory tree through the platform API where its std has none, as a `hand` cell that says so.
  - A language with none of these has no source, and its `skip` names the missing facility.
  - `labels` may give a language a label, printed beside each of its cells in a Label column: a fact of its library at the row's target that the row does not change, such as app/archive's Zig cells, which run software AES, GHASH and SHA-256 at x86-64-v2.
- **Ratios.** Each cell gets its ratio of medians to the fastest cell of the row and to the fastest cell of its kind. An `eco` cell runs mostly its libraries' code, which its column's flags do not make checked (C and assembly in `ring`, unsafe Rust in `regex`), so its class is printed "eco (not classed)" and it enters no class ratio; a `std` or `hand` cell keeps its column's class. The table's ratios never feed the median mk / c or the 1.10 bar.
- **The defect line.** The table has no verdict. Each Mk cell's ratio to the fastest `std` cell of C, Rust, Zig, Go and C# is classified against 2.0 by its 95 percent interval: over 2.0 is a std defect for the std function the row's profile names. A row with no such cell says so.
- **Columns.** `mk`, `c`, `rust`, `rust-ovf`, `zig-fast`, `zig-safe`, `go`, `cs` and `cs-aot`, for each language with a source. There are no `mk-wrap`, `mk-keyed`, `mk-ctx` or check-budget columns (a source for one of the first three is refused): check budgets are the `same` table's.
- **The program's own source keeps every ban of the other tables** (`otherTableViolations`): no unchecked indexing, no `unsafe` in Rust, no `@setRuntimeSafety(false)`, no fast-math, no hints or per-language tuning. Mk's program may call `std.simd`'s routines that choose their vector form inside std at run time (`IndexByte`, `IndexAny`, `Count`, `Equal`, `Compare`, `ValidUtf8`, `Dot`, `Sum`), as Go's program calls `bytes.IndexByte`: std's own dispatch is std's. In a row with a twin, it may not write vector code of its own (any other `std.simd` name, a `cpu` clause, a `Cpu()` test) or declare an unsafe module. A row with no twin (Tier A, below) compares Mk with itself, so a dogfood that does either (imgproc's vector code, kvd's `src/snap`) can be such a row unchanged, labelled: its README names the vector code or the unsafe module it keeps. It cannot be a twinned row, with one exception: `app/kvserve` takes kvd unchanged, with `src/snap` (its snapshot recovery through `fs.Map`) labelled in that row's README. Its server spec names kvd's one unsafe module, `src/snap`, in `unsafe_modules` and says in `unsafe_why` why the measured work never reaches it, and the check passes the row only while the package declares exactly the modules named. Only a server spec has these fields, so a `bench.json` row has no such exception. `TestTreeRowsMeetTheContract` applies them to every file of the program's own source (`appRowViolations`): every `.mk` file of the Mk package (a dogfood's whole package, nested packages aside), every `.rs` file under a crate's `src`, and the one file of each other twin, which opens with the row's header comment. The libraries are outside the check, and their contents are labelled instead.
- **The Mk side.** A new Mk program sits under `mk/`, written from the documents only, as a user would, and frozen before its first publish. A dogfood is used unchanged through `package`: `{"path": "Dogfoods/<name>"}`, repository-relative, with `"bin"` naming one bin of a package that has several (`mk build --bin`). Its files enter the build stamp, results.json records the last commit that touched it and whether the tree differs there, and an edit to it is checked for function, not speed. Gains come from the compiler or std, as in `same`.
- **Offline and pinned.** Nothing is fetched at bench time.
  - **Rust.** `sources.rust` may name a crate directory: a `Cargo.toml` naming one package, its `Cargo.lock`, and `src/main.rs`. tools/bench builds it with `cargo build --release --offline --locked --target x86_64-pc-windows-msvc`, the rust column's flags given as the release profile through `--config` (opt-level 3, one codegen unit, fat LTO, panic abort, overflow checks on in `rust-ovf` only), `-C target-cpu=x86-64-v2 -C target-feature=+crt-static` through `CARGO_ENCODED_RUSTFLAGS` (with `--target`, they reach the program's crates only, not build scripts or procedural macros), and each column's own `CARGO_TARGET_DIR` under the work directory. `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, the wrappers, `RUSTC`, `RUSTUP_TOOLCHAIN` and every `CARGO_PROFILE_*`, `CARGO_BUILD_*` and `CARGO_TARGET_*` variable are removed from the caller's environment, and cargo is given `RUSTC`, the rustc whose version the build records. The crate's `Cargo.toml` has one form, checked line by line, and anything else is refused: a `[package]` table, then optionally `[dependencies]`, and no other table; no key before `[package]`; in `[package]` only `name`, `version`, `edition`, `publish`, `description` and `license`, each a bare key with a plain value; in `[dependencies]` a bare name with a version string, or a one-line inline table of `version`, `features` and `default-features`. So no profile, build script, target, `[workspace]`, `[lib]`, `[patch]`, `[replace]`, `[[bin]]`, path, git or workspace dependency reaches cargo in any spelling TOML has (a dotted, quoted or inline-table key, a quoted table header), and a quoted key, a literal string and a multi-line value are refused outright. The crate may not have a `build.rs`, a `.cargo` configuration or a toolchain file. A cargo configuration or toolchain file in a parent directory or in `CARGO_HOME` is the machine's, not the row's: it refuses the crate's build, a failed build like any other (publish and verify report that cell failed, and compare stops at it), and every row still loads. Every package of `Cargo.lock` but the crate comes from the registry with a checksum, a crate that links any is an `eco` cell whose `libs` names each direct dependency, and every library `libs` names must be in `Cargo.lock` at that version. A variant's crate is checked the same way. The lockfile is in the build stamp, and so is every file of a row's `crates` tree (below); a cargo build that runs at all (its stamp changed or missing) first empties the column's `CARGO_TARGET_DIR`, because cargo takes a directory-source package at an unchanged version as fresh and would reuse its old build. rustup's own per-directory overrides (`rustup override set`) are not read.
  - **The evidence directory.** Rows with third-party sources read them from the evidence directory, `MK_EVIDENCE` (default: `Mk-evidence` beside the repository), which the repository does not ship. Without it, those rows are skipped with the reason.
  - **Where crates come from.** The local cargo registry (`CARGO_HOME` stays the user's); `Cargo.lock`'s checksum pins each crate's SHA-256. A crate the registry lacks is fetched once, for the rows that need it, and recorded in the evidence directory with its SHA-256 and a `SOURCE.txt`.
  - **Crates pinned in the evidence directory.** A row's `crates` names a directory under it, relative and slash-separated (`crates/flate2-1.1.1`). That directory holds:
    - the crates in a `cargo vendor --versioned-dirs` layout, one `<name>-<version>` directory per package;
    - the crates.io archive of each package, in `archives/<name>-<version>.crate`;
    - a `.cargo/config.toml` of exactly four lines, as `cargo vendor` prints them: `[source.crates-io]`, `replace-with = "vendored-sources"`, `[source.vendored-sources]` and `directory = "<a relative path in the same directory>"`.
  - **How cargo reads them.** tools/bench checks that file (any other line refuses the build) and hands it to cargo as `--config <file>`.
    - Cargo then reads crates-io's packages from that directory only, by directory source replacement, never from the user's registry.
    - Cargo resolves the relative directory against the parent of `.cargo`.
    - The build stays `--offline --locked`.
  - **Why tools/bench pins the tree.** What cargo checks is narrower than a pin. It compares `Cargo.lock`'s checksum with the `package` field that each vendored package's `.cargo-checksum.json` declares for itself, and each file with that JSON's own `files` map. Nothing ties the files to the `package` SHA-256, so a file changed together with its `files` entry builds. So before every cargo build, tools/bench checks:
    - every registry package of the crate's `Cargo.lock` has its archive, whose SHA-256 must be the lockfile's checksum;
    - its vendored directory holds exactly the archive's regular files, byte for byte, beside its `.cargo-checksum.json`. Only a top-level `.gitignore`, `.gitattributes` or `.cargo-ok` may be missing. Cargo 1.99.1's vendor was seen to drop `.gitignore` only, from the 8 of the rows' 15 archives that have one; the other two are version-control and unpack files that no build reads;
    - the vendored directory holds those packages and nothing else.

    Any difference refuses the Rust cells' build, naming the file. The field is checked when the row loads, and the directory when a crate is built, so a tree missing from the evidence directory fails the Rust cells only. A configuration file in or above the crate, or in `CARGO_HOME`, is still refused (above).
  - **C.** Libraries come from the evidence directory through `vendor`: `files` are paths under its `dir`, whose last element may be a pattern (`lib/common/*.c`); every `.c`, `.S` and `.s` file goes on the C line with `-I<dir>`, `-I` for each `include` directory, and `c_flags`. On an app row a library is C's alone, so `vendor` needs `"for": ["c"]`, and C's cell is then `eco` with the library in `libs`. `"for": ["c"]` keeps a library off the Mk side: no package copy, none of its files in the Mk stamp, and no comparison with the Mk package's `CSource` flags (that comparison is for a library both sides compile).
- **Environment.** `env` adds variables to every program of the row after `runEnv`: a single-threaded row's `MK_CARRIERS=1`, for example. It may not set what `runEnv` pins or clears (`MK_IO` among them), except `MK_CARRIERS`, nor `MK_STD`, `MK_CACHE` or `MK_TEST_*`, and a concurrency row's `MK_CARRIERS` comes from its thread count. Single-threaded rows keep `publish`'s one-CPU affinity, and a program with a parallelism flag runs it at 1; a parallel variant is a concurrency row. `compare` runs each program with the row's environment too.
- **The checksum.** With `"digest": true` the checksum is `sha256:` and the SHA-256 of the program's whole standard output, CR LF read as LF, with the data path and the column's output path, in either slash form, written back as `$DATA` and `$OUT`, so it does not depend on where the work and data directories are. Without it, the checksum is the trimmed output, as in the other tables. Either is recorded in bench.json as `checksum`, and every column must print it.
- **Output files.** `output` names a file the program writes: `file` is its name, and `{out}` in `args`, `quick` or `then` is the column's own path for it under the work directory. It is deleted before every checked run and, when timed, by hyperfine's `--prepare` before every run, which hyperfine runs through the platform shell, so the path is quoted and may hold no quote, `%` or line break. `check` says what the checksum gains from it:
  - `digest`: `file sha256:` and the file's SHA-256;
  - `zlib` or `gzip`: a round trip. Go's `compress/zlib` or `compress/gzip` decodes the file, the result must equal the row's data file byte for byte, and the checksum gains `roundtrip sha256:` and its SHA-256. Compressed bytes legitimately differ by library, so they are never compared; their size is printed beside each cell.
  - `then` names a second, untimed run of the same program after each checked run (an archive's `open` after its `create`); its standard output stands for the checksum's output part.
  - `then` as the check: the file is the program's own format, whose bytes legitimately differ by library (an archive's DEFLATE stream), so the checksum gains nothing from it, and the `then` run, which reads the file back, is the check: its standard output, digested as above, must be every column's. `then` must be given. The file's size is printed beside each cell. `then` must name `{out}`. A column's own `then` shows only that it agrees with itself, so `verify` also runs each passing column's `then` on every other passing column's file, untimed, and each of those runs must print the checksum too: a column whose writer and reader are wrong in the same way fails. A failed pair is judged by the languages other than the reader's and the file's, each counted once, since a language's two columns (rust and rust-ovf, zig-fast and zig-safe) build one source; a language reads the file when each of its passing columns prints the checksum on it. When most of them read the file, the pair is the reader's error; when most fail on it, the file's column's; on a tie, or with no other language, both columns are marked. `verify` prints, and `publish` logs, one line with how many pairs ran and how many printed the checksum. A row with `then` as its check specifies the file's format in its README.
  - A variant has no data file of its own, and a round trip compares with the row's data file, so a compress and decompress pair (zlib's `c` and `d`) is two rows, each with its own `data`.
- **Peak memory.** Each checked run, which is untimed, reads the program's peak memory: on Windows the peak working set and the peak commit (psapi's `GetProcessMemoryInfo` through `syscall`, on a handle tools/bench opens itself, the structure's address read from `fmt`'s `%p`, so neither `unsafe` nor `reflect` is imported, as `internal/archtest` requires), on Linux `ru_maxrss` read through a spawner. On Linux the child Go starts shares its parent's address space until its exec (clone with `CLONE_VM`), and the kernel folds that address space's peak into the child's `ru_maxrss`, so read by tools/bench itself a peak is at least tools/bench's own size. So tools/bench runs each program through a spawner, a small process that starts the program, reads its `ru_maxrss`, and reads its own peak (`VmHWM`) after the program's exec: the floor. The spawner is `tools/bench/peakspawn`, a minimal Go program that `publish-linux` builds beside benchtool with benchtool's flags; only when none is beside it (as in a test binary) is it a fresh copy of tools/bench itself, whose floor is higher, and tools/bench then says so on its standard error. peakspawn's floor is 1,536 to 1,792 KiB, and the fallback's, in the benchtool that publish builds, 4,480 to 4,608 KiB (measured in WSL 6.6.87.2 on 2026-11-16). A reading above the floor is the program's own `ru_maxrss` figure: its process and the children it waited for. A reading at or under it only bounds that figure, and the cell prints `at most N MiB`, N the reading rounded up; `-` means no reading. results.json keeps the raw reading, the floor and the spawner of each Linux cell (`maxrss_bytes`, `spawner_floor_bytes`, `spawner`), and each app row says in one sentence how its Linux peak was read. The spawner's start-up is inside the checked run's printed wall time, which is not a timed figure. hyperfine 2.0.0 can record a peak resident set of its own (`--help`: `memory_peak_resident`), but tools/bench reads the peak itself: on the untimed run, so reading it costs no timed run anything, and with the Windows peak commit, which hyperfine's metrics do not list. It is printed as a fact column, never as a ratio, and it gates nothing.
- **Inputs.** Besides `words`, `log`, `json` and `gzip`, `tools/bench gen` has five kinds for this table (`tools/bench/gen_app.go` and `gen_orderfeed.go` state each):
  - `tree`, a directory of source-like text in nested directories (under extensions no tool of the repository reads as source, since `data/` is not a `testdata` directory), with hidden names, binary files, CR LF files, capitalised names, and keywords and UTF-8 lines for a search;
  - `jsonl`, an NDJSON event log of integers and strings, ASCII only, with escapes, and with no `<`, `>` or `&` that a library might write differently;
  - `mixed`, text, structured binary, random bytes and runs, in 64 KiB blocks;
  - `zlib`, another kind (`"of"`, `words` when absent) compressed by Go's `compress/zlib` at level 6.
  - `orderfeed`, a market-data feed in the orderbook dogfood's format for `app/orderbook`: every command kind and every refusal reason, prices with no, one and two decimals, comments, LF line ends and no quote.
- **Tier A.** A row with an Mk source only (a dogfood at scaled arguments) is compared across mk binaries by `compare`, as a provisional pair. Published, it is a one-cell row with no peer and no defect line. A "Mk across versions" section of RESULTS.md does not exist yet.
  - Rows: `pack`, `kvd` (its `sim`; its README says why not `bench`), `textkit` (`grep` and `wc`), `lox`, `tracer`, `imgproc`, `bigcalc`, `raft` and `cron`, each its dogfood unchanged, with `MK_CARRIERS=1` and a digest, and a README that says it is an Mk-only row and names what it keeps that a twinned row may not (imgproc's vector code and dispatch, kvd's `src/snap`). `TestTierARowsAreDogfoods` checks them.
  - orderbook and mgrep have no row of their own: their Tier A pair is the Mk column of their twinned rows, `compare -cols mk orderbook` and `compare -cols mk grep-re grep-lit grep-ci`, which run the dogfood unchanged on the same input. So `app/orderbook` keeps its name, and one dogfood is one row.
  - `{pkg}` in an app row's arguments (and in `then`) is the absolute directory of the package the row names, so a row passes the dogfood's own input files (`{pkg}/cases/data/busy.tab`) to it unchanged; a row that names no package is refused when it loads, and the digest writes the directory back as `$PKG`.
  - The quick arguments:
    - They follow the dogfood's own cases, except in pack and textkit, whose size is their one data spec.
    - imgproc, raft, tracer and cron run their bench case's arguments, with `{pkg}` and `{out}` for its `$CASES` and `$WORK`.
    - lox and bigcalc give their bench case's input on the command line instead of its file, so their quick output can be read against the dogfood's `cases/bench.out`. lox gets `cases/scripts/bench.lox` through `--eval`; bigcalc gets the lines of `cases/data/bench.rpn` to `calc`, where the case runs `run` on the file.
    - kvd takes its `sim-carriers16` case's seeds with `MK_CARRIERS=1`, where the case sets 16.
    - The publish arguments are provisional until `verify -publish-size` runs on a quiet machine.
- **Server rows.** A row whose program is a server has a spec `app/<row>/<row>.json` instead of a `bench.json`, since hyperfine cannot time a server, so `list`, `verify` and `publish` never see it.
  - Its fields: the app row's (`package` or `sources.mk`, `kinds`, `hand`, `skip`); each language's `models`; `args`, every column's command line, with `{port}` and `{data}` (a fresh empty directory per server start); `mk_args`, a dogfood's own flags, after `args` in the Mk column only; the http row's load fields (`connections`, `warmup_s`, `measure_s`, `server_mask`, `client_mask`, `threads`, `sweeps`); a `seed`; `check_requests`; and one load, `kv` or `api`.
  - tools/bench's generator keeps one request outstanding on each connection, as the http row's does. Each connection owns its own keys or items, so its session checks every reply against its own model of the server.
  - A row may also check what the server leaves behind once it is stopped: kvserve's write-ahead log, replayed, must give exactly the connections' models.
  - `TestServerRowsMeetTheContract` applies the app table's contract (`appRowViolations`, with a row's labelled unsafe modules) to every server row.
  - A server row's few sweeps give no 95 percent interval, so its defect line (`serverDefect`) reads the sweeps' range instead. The rule is provisional: over 2.0 only when every pair of sweeps is over it, within only when every pair is at or below it, inconclusive otherwise.
  - Its "over" blames the row's program and std's server path together, not one std function: a server spec names no profile, and the program's own work is in the Mk cell.
  - `tools/bench kv -check` (or `http -row httpapi -check`) builds every column and runs `check_requests` requests on each connection, every reply checked, timing nothing: the check to run before any timing.
  - `tools/bench kv` runs a short unpinned window and prints provisional numbers.
  - `kv -publish` measures under the machine lock, pinned as `http`, and writes `results/<date>/<row>/results.json` and the row's section of RESULTS.md (`serverbench.go`).
  - Rows: `kvserve` and `httpapi`.
- **Not in tools/bench yet:** the "Mk across versions" section.

## Compile speed

`tools/bench compile` (`tools/bench/compile.go`) generates one program of the same shape in C, Rust, Zig, Go and Mk into `<work>/compile/<lang>/src`, never into the tree, and times its builds. `compile -quick` checks every build on a small program; `compile -publish [-date D]` takes the machine lock and writes `results/<date>/compile/results.json` and the section "compile" of RESULTS.md.

- **The program.** `-modules` modules (50) of `-structs` structs (8) and `-funcs` functions (40), about 36,000 lines in each language. Function `F<j>` of module `i` builds a struct, runs a four-step loop and a branch, calls its module's private helper and, for `i > 0`, `F<j>` of module `(i - 1) / 2`: imports form a binary tree, so independent modules can build in parallel. `main` calls all 2,000 functions and prints a wrapping sum, which tools/bench computes itself (`genSpec.checksum`) and checks after every build, so a stale incremental build fails the cell instead of being timed. Every language has one compilation unit per module where it has units: C a translation unit, Rust a module of one crate, Zig a file, Go a package, Mk a module directory.
- **Builds.** Each language's default dev and release profiles, not the run-time table's flags; the target is x86-64-v2 everywhere. C: CMake's Debug (`-g`) and Release (`-O3 -DNDEBUG`) flags, one TU per module, compiled 8 at a time by tools/bench acting as make (a TU whose object is older than its source is compiled), linked by lld. Rust: `cargo build [--release] -j 8`, its default profiles (dev incremental, release 16 codegen units, no LTO). Zig: `zig build-exe -O Debug` and `-O ReleaseFast`, `-j8`. Go: `go build -p 8`; Go has one profile, so its release row says so. Mk: `mk build -j 8` and `--release --pgo=off -j 8`.
- **Clean and edit.** Clean deletes every cache and object of that language and profile first: C's objects, Rust's target directory (std stays precompiled, as Rust ships it), Zig's local and global caches (so compiler_rt and the MinGW C runtime are rebuilt), a fresh GOCACHE and `go build -a` (so the std packages the program imports are rebuilt), a fresh MK_CACHE. Edit changes one constant in the body of `F20` of module 25 and rebuilds with the caches warm; each edit writes a value no earlier build saw, so a content-addressed cache cannot serve it. Per cell: 3 clean builds and 10 edit builds after 2 untimed ones (`-clean-runs`, `-edit-runs`), median, minimum and MAD of the wall time from the first compiler start to the executable.
- **Machine.** 8 jobs on 8 cores: publish sets tools/bench's affinity to `0x5555` (one logical CPU on each of the 8 cores; Windows numbers SMT siblings next to each other), inherited by every compiler. Ratios are to the fastest cell of the same profile and kind.
- **The bar.** Mk's rank in each cell (profile and kind) must be no worse than its rank in the baseline publish. The ratios are reported.
- **No change.** After the edit builds, and without changing them, each language rebuilds with nothing changed (`-warm-runs`, 5 after 1 untimed), checked the same way: what each tool does when nothing needs doing. C's make then runs nothing, because the executable is newer than every object, and its cell says so, with no time or ratio (nor is it the best of the kind); an edit always recompiles a translation unit, so every edit build still links.
- **Edit to diagnostic.** For Mk's dev profile only, two `mk check -j 8` rows in the dev build's cache (`-check-runs`, 10 after 1 untimed pair), against the two "Edit to diagnostic" compile budgets. Body edit: the edited function's constant is replaced by an unknown name, which gives one diagnostic, after a valid body edit. Signature edit: a new exported function in `m0`, the root of the import tree, which every other module imports through its parents and `main` imports directly, so the module's interface changes and every module is an importer; no function body changes between the timed state and the one before it, which is the same function with a parameter of an unknown type. Every timed check follows a state with the opposite verdict, and the bad one must exit 1 and quote its unknown name, so a check that did not read the edit fails the cell. No other language's command is timed here.
- **Against the budgets.** When a table has these rows, RESULTS.md lists each "Compile speed" budget that one of its Mk cells measures (the edit-to-diagnostic rows, the COFF or ELF one-function edit, the clean dev build, and the release edit and clean). A row gets a verdict, the median against the bound, only when the program is within 10 percent of the size the budget is stated at (100 KLOC, or 1 MLOC for the body edit); otherwise it says the program's size. Every budget is a proposal, and a miss is written down with a plan. The Windows clean dev cell is the whole build, std included, where the budget says "user code", so it is an upper bound of what the budget times: at or under the bound it prints "met" with that said, and over it "no verdict: the cell includes std", never a miss.
- **Linux.** The ELF edit budget (200 ms at 100 KLOC) is measured inside WSL 2, by an mk built for Linux (`GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build ./cmd/mk` at the commit measured) building for x86_64-linux with ld.lld, on the Linux file system:

  ```
  pwsh -NoProfile -File tools/wsl-lock.ps1 <benchtool.exe> compile-linux -mk <linux mk> [-modules 139] [-date D]
  ```

  On Windows, `compile-linux` refuses to start outside the WSL lock (`MK_WSL_LOCKED=1`), refuses a `-linux-work` under `/mnt` and an `-mk` that is not an ELF file, takes the machine lock for the whole run, builds `tools/bench` for Linux, and runs `wsl.exe --cd <repo> -e taskset -c 0,2,4,6,8,10,12,14 <benchtool> compile -platform linux -no-lock -publish -langs mk ...`. Inside WSL that copies the mk to the Linux work directory (default `/tmp/mk-bench-compile`) and runs this table's Mk builds there, with every kind above, into `results/<date>/compile-linux/results.json`, rendered after the Windows table. `taskset` pins 8 virtual CPUs of the WSL 2 machine, not 8 cores, and the table says so. The other languages' builds are the Windows table's only.

### Real programs (`compile -real`)

`tools/bench compile -real [-programs kvd,lox,orderbook,pack] [-vs base=<mk>,...] [-publish [-date D]]` (`tools/bench/compile_real.go`) times Mk's builds of real programs that use std, which the generated program does not: generics, `mono`, the instance-limit walk and std's front end. Mk only: there is no twin, so the table compares mk binaries, the one measured (`-mk`, labelled `-head-label`, default `head`) and older ones (`-vs`), each in its own caches, interleaved per program and profile, every ratio to the measured one.

- **Programs.** kvd, lox, orderbook and pack, dogfoods of `Dogfoods/` with one bin each, used unchanged: their `pkg.mk` and `src/` are copied into `<work>/compile-real/<mk>/<program>/<profile>/src` before every clean build (without the `gen/` views `mk build` writes, or a PGO profile), and results.json records each package's last commit, whether the tree differs there, and its lines of Mk.
- **The edit.** One string literal of the program's help output, inside a function body (`Main`, or a function `Main` calls; never a module-level `const`), gets a token that is new at every build, `mkbench-edit-<n>` and a line feed; after every build tools/bench runs the help command and finds the token, so a stale build fails the cell. `TestCompileRealSites` checks, with no build, that each site is there exactly once, indented, in a package with one bin.
- **Builds.** `mk build -j 8 --cpu x86-64-v2` (dev) and `--release --pgo=off` (release), the generated table's Mk line. Per program, mk and profile: 3 clean builds (a fresh MK_CACHE, so std is checked and compiled again), 10 edit builds after 2 untimed, 5 no-change builds after 1 untimed, and in dev an edit-to-diagnostic row: `mk check -j 8` after a valid edit, untimed, then timed on the next edit, which writes an unknown name in place of the literal and must exit 1 naming it. Affinity, the lock and the facts are the generated table's.
- **Across versions.** An older mk that cannot build today's program has that cell excluded with its reason, which is a fact of the table, not a failed run; a failure of the measured mk fails the run. The table has no bar (the rank bar is the generated table's), and nothing in it feeds another table.
- Results go to `results/<date>/compile-real/results.json`, and RESULTS.md gets the section "compile-real", carried like the others.

### Build time of the benchmark programs (`buildtime`)

`tools/bench buildtime [-table same|idiomatic|app] [-runs 3] [rows]`, with `-publish [-date D]` under the machine lock (`tools/bench/buildtime.go`), times how long each column of the tree's `same`, `idiomatic` and `app` rows takes to build the executable its run-time table times (a `tests/bench-lanes` row only when named, and a name no run-time table has is refused). It runs on Windows only, and a failed cell of the mk measured fails the run. It answers how long each language takes to build what was measured, not how fast its compiler is: that is the generated table's question, in each language's default profiles.

- **Flags.** Each column's own run-time command line (README "Columns", unchanged, so no run-time build's stamp moves). They are not each language's default profile, and they differ in kind: Rust builds with fat LTO and one codegen unit, C one translation unit with no LTO, Zig one compilation unit, Go its whole program, Mk ThinLTO with std compiled with the program. The table's legend gives each column's LTO, linker and what its build compiles of its std.
- **Empty caches**, as the compile table defines them, applied to those command lines. Every build runs in a fresh directory of its own, which holds:
  - the Mk cache (and Mk builds `--no-cache`);
  - Zig's local and global caches, so compiler_rt is rebuilt;
  - a crate's cargo target directory, so its dependencies are built from source.

  Go gets a fresh GOCACHE, so the std packages the program imports are rebuilt. Rust's std stays precompiled, as Rust ships it, and C's UCRT is prebuilt. rustc on one file and C keep no cache.
- **Timing.** 3 builds per cell, forced (no stamp), one at a time, each build's directory removed once its time is taken (and, for the first, its program checked), wall time from the compiler's start to its exit (plus the copy of cargo's product), under publish's 8-CPU affinity `0x5555`, each compiler at its default parallelism. The first build's program is checked at the row's quick size before its times count; a wrong program, or a row with no quick checksum to check it against, excludes the cell with the reason.
- **Reading it.** Each cell's median, with no ratio between cells: the columns' flags differ in kind, so a ratio across them would read as a compile-speed ratio, which this table is not. No class, no bar, and nothing in it feeds the median mk / c, a class ratio, the std bars or the compile tables.
- Results go to `results/<date>/buildtime/results.json`, and RESULTS.md gets the section "buildtime", carried like the others.

## Linux

The Linux table is Mk against C only, on the same rows. The C baselines call `printf`, `malloc` and `strtoll`, so a `-nostdlib` cross-build cannot build them; instead the C side is built inside WSL by clang 21 from apt.llvm.org (installed there with lld 21 if missing, and the version recorded) against glibc, with the same flags as the Windows column apart from the target (`-std=c17 -O3 -march=x86-64-v2 -ffp-contract=off -fuse-ld=lld -static`, then `-lm` after the source, since static glibc keeps `sqrt` in libm). ## Reading a row's code

Before any change for a row's speed, its time is attributed and its code read beside the C twin's. `tools/bench ir` does the reading part for one same-algorithm row, on Windows:

```
go run ./tools/bench ir -mk <mk.exe> -work <dir> [-func Build,Check] [-cfunc build,check] <row>
```

- It builds the row's `mk` and `c` columns with the row's own command lines (the ones `verify` and `publish` run) into `<work>/ir/<row>/`, removed first, and writes `index.txt` there (also printed). A row with no `c` source, as most std rows are (`std-mem2/fixed`, `std-hash/mappair`), is read on Mk's side alone: no `c-ll`, `c-remarks.txt`, `c.exe`, `c.map`, `c-disasm.txt` or `side-by-side.txt`, and `index.txt` lists only Mk's files (`TestIRViewMkOnlyRow`). It holds no lock, times nothing and writes nothing under `tests/bench`, so it may run on a loaded machine. Its outputs are facts of the two builds (IR, remarks, instructions), never a benchmark number. Pass `-work` (the default is the shared bench work directory) and `-mk` (otherwise it builds `./cmd/mk` into the work directory).
- Mk: the `mk` line plus `--llvm <shim>` and the hidden `--emit-ll <dir>`. The shim (`tools/bench/shim.go`) runs the real clang and lld-link and only adds options that change no emitted byte: remarks on each ThinLTO backend, the import report on the index step, `/lldmap` on the final link. `TestIRViewRow` checks that the executable is byte-identical to the row's plain build. The outputs:
  - `mk-ll/<bin>/p*.ll`, `support.ll`: the pack IR codegen wrote.
  - `mk-lto-ll/m<i>.o.ll`: each module's IR after import and the backend's -O3, as it reaches code generation. The backend is rerun with `-S -emit-llvm`, and module `m<i>` is pack `p<i>`.
  - `mk-remarks.txt`: the backends' `-Rpass=loop-vectorize|loop-unroll -Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize` remarks and `-mllvm -print-imports`.
  - `mk-imports.txt`: the index step's `/mllvm:-print-imports /mllvm:-print-import-failures`, which lists the missed imports with their reason and threshold.
  - `mk-commands.txt`: every LLVM command of the build.
- C: the `c` line plus `-Wl,/lldmap:`, and the same compile with `-S -emit-llvm` and the same remarks (`c-ll/`, `c-remarks.txt`). The C column is one translation unit without LTO, so this is its final IR.
- `-func` names hot functions: an exact symbol, the last segment of an Mk name (`Build` for `mk.main.Build`), or a substring. `-cfunc` gives the C names when they differ. For each match, `mk-disasm.txt` and `c-disasm.txt` hold llvm-objdump's disassembly of the function's range in the lld map, without the alignment padding, and `side-by-side.txt` pairs the first match of each. A release image has no symbol table, so the map is what names the code. Without `-func`, the index lists each executable's 15 largest functions. The hot loop is often inlined into its caller (`Main`), so name the caller when the loop's own function is missing.
- It does not cover the codegen kernels (`tools/bench codegen`) or the Linux target. For those, read the pack IR with `mk build --emit-ll` by hand.

### Profiling a row

Use a sampling profiler on the hot function before reading its code, and use the counting builds to fix what a row executes. A profile attributes time. It is not a published number, so it may be taken on a loaded machine, though a quiet one gives cleaner samples.

1. **What runs.** `go run ./tools/bench verify -mk <mk.exe> -work <dir> <row>` builds every column, checks the checksums and, for a row with `counts`, runs every language's counting build at the quick size and requires one `counts` line from all of them (above). Two columns that agree there execute the same operations, so a time difference is the code's.
2. **Windows: Windows Performance Toolkit (xperf and WPR).** On the measuring machine, `xperf.exe` (10.0.26100) and `wpa.exe` (WPA 11.7) are in `C:\Program Files (x86)\Windows Kits\10\Windows Performance Toolkit`, and `wpr.exe` (10.0.26100) is in `C:\Windows\System32` (2026-11-15, from the files' version resources). Kernel sampling needs an elevated shell. Build the program with symbols. `--debug` puts a PDB beside the executable, and on binarytrees the release code was instruction-for-instruction that of the plain build: the only differences were 30 import-thunk displacements (`jmpq *disp(%rip)`, one per thunk; a raw `diff` shows a 31st line, objdump's header naming the file), because the debug directory shifts `.rdata` (2026-11-15, `llvm-objdump -d --no-show-raw-insn` of both, addresses stripped, counted twice). For C, add `-g` to the row's `c` line, and clang passes `/debug` to lld-link.

   In PowerShell:

   ```
   mk build --release --pgo=off --cpu x86-64-v2 --debug -o <dir>\mk.exe tests\bench\same\<row>\mk
   xperf -on PROC_THREAD+LOADER+PROFILE -stackwalk Profile -f <dir>\kernel.etl
   <dir>\mk.exe <the row's args>
   xperf -d <dir>\trace.etl
   $env:_NT_SYMBOL_PATH = '<dir>'
   $env:_NT_SYMCACHE_PATH = '<dir>\SymCache'
   xperf -i <dir>\trace.etl -symbols -o <dir>\profile.txt -a profile -detail
   ```

   Without `-f`, `xperf -on` logs to `\kernel.etl` at the root of the current drive, and without `_NT_SYMCACHE_PATH`, `-symbols` writes its cache to `\SymCache` (xperf's `-help start` and `-help symbols`), so both are set to keep every file in `<dir>`. In cmd the two variables are `set _NT_SYMBOL_PATH=<dir>` and `set _NT_SYMCACHE_PATH=<dir>\SymCache`. `-a profile -detail` buckets the samples by process and function. WPA (`wpa <dir>\trace.etl`, CPU Usage (Sampled), with the symbol path loaded) gives the same samples by function, call stack and address. `wpr -start CPU -filemode` and `wpr -stop <dir>\trace.etl` record the same kind of trace as the `xperf -on` and `-d` pair. Without a PDB, `xperf -i trace.etl -a dumper` lists each `SampledProfile` event's program counter, and the image's load address subtracted from it is an RVA in `bench ir`'s lld map. These commands were checked for syntax (`xperf -help`, `xperf -i <existing trace> -a dumper`) on 2026-11-15. No trace of a row was recorded, because timing waits for the quiet machine.
3. **Linux (WSL): `perf`.** The distribution is Ubuntu 24.04.3 on the WSL kernel 6.6.87.2-microsoft-standard-WSL2, with `perf_event_paranoid` 2 and the `cpu` PMU listed. perf 6.8.12 is installed (`/usr/local/bin/perf`, linked from `linux-tools-generic`), and `perf stat -e cycles,instructions` counts `cycles:u` and `instructions:u` (checked on 2026-11-15 under `tools/wsl-lock.ps1`). Every WSL command runs under the lock. No row has been profiled with it yet, so the commands below are not run:

   ```
   mk build --release --pgo=off --cpu x86-64-v2 --debug --target x86_64-linux -o <dir>/mk tests/bench/same/<row>/mk
   perf record -e cpu-clock -F 999 --call-graph dwarf -o <dir>/perf.data -- <dir>/mk <the row's args>
   perf report -i <dir>/perf.data --stdio --sort symbol
   perf annotate -i <dir>/perf.data --stdio <symbol>
   ```

   A release ELF without `--debug` is linked with `--strip-all`, so the profiled build takes `--debug` to keep its symbols. On binarytrees the cross-built ELF's `.text` was the same with and without `--debug`, at the same addresses (2026-11-15, `llvm-objdump -d -j .text` of both, symbol annotations removed). The call chains come from the `--debug` build's DWARF (`--call-graph dwarf`), not from `-g`, which unwinds by frame pointer: Mk code keeps none (on binarytrees' x86_64-linux release `.text`, no `movq %rsp, %rbp` against 135 `retq`, and the pack IR has no `"frame-pointer"` attribute; 2026-11-15, `llvm-objdump -d`), so `-g`'s stacks are unreliable for it. The self samples by symbol do not depend on the unwinder. `cpu-clock` is a software event, so it samples even where a virtual machine exposes no hardware counters. This VM counts `cycles` (above); sampling on `-e cycles` was not tried. `perf stat -e cycles,instructions -- <dir>/mk <the row's args>` gives instruction and cycle counts. Such counts may guide a development decision, since machine load moves them little, but they are not a published number, which comes only from `tools/bench`.
4. **Read the code.** Run `go run ./tools/bench ir -mk <mk.exe> -work <dir> -func <the hot function> <row>` (the row last: flags after it are not read), then compare the hot loop's instructions and the two remark files, and Mk's `mk-lto-ll` with C's `c-ll`.
